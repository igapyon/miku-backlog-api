# Backlog APIのレート制限

- 確認日: 2026-07-22
- 対象: Backlog API v2

## 公式仕様として確認できる事項

Backlog APIのレート制限は、APIキー単位ではなくユーザー単位で適用されます。
同じユーザーが複数のAPIキーを使用しても、APIキーごとに独立した制限枠が
与えられるものとして扱ってはいけません。一方、同じスペースを利用する別の
ユーザーは、それぞれのユーザー単位で制限を受けます。

制限枠は次のリクエスト種別ごとに分かれています。

- `read`: アイコン取得および検索API以外のGETリクエスト
- `update`: POST、PATCH、DELETEリクエスト
- `search`: 課題一覧・課題数・Wikiページ一覧・Wikiページ数などの検索API
- `icon`: スペース、ユーザー、プロジェクト、グループ、チームなどのアイコン取得

上限値はリクエスト種別とBacklogのプランによって異なり、Backlog側の負荷状況に
よって一時的に引き下げられる場合があります。上限を超えた場合はHTTP `429`
（Too Many Requests）が返されます。

すべてのAPIレスポンスには、次のヘッダーが付与されます。

- `X-RateLimit-Limit`: 現在適用されている上限
- `X-RateLimit-Remaining`: 残りリクエスト数
- `X-RateLimit-Reset`: 制限がリセットされる時刻を表すUTCのUNIX秒

`GET /api/v2/rateLimit`を呼び出すと、`read`、`update`、`search`、`icon`の
それぞれについて、`limit`、`remaining`、`reset`をまとめて取得できます。

## スペースをまたぐ場合

公式資料で明記されている制限単位は「ユーザー別」です。しかし、同じNulab
アカウントが複数のBacklogスペースを利用する場合に、制限枠がスペース間で共有
されるか分離されるかは、確認した公式資料には明記されていません。

また、レート制限情報は各スペースのAPIエンドポイントから取得し、上限はスペースの
プランにも依存します。このため、実運用では安全側の推定として、次の単位で状態を
個別管理します。

```text
対象スペース × 認証ユーザー × リクエスト種別
```

これは公式仕様として保証された境界ではありません。同じユーザーが複数スペースを
利用する場合は、各スペースで`GET /api/v2/rateLimit`を実行し、それぞれの値を
独立して確認するのが確実です。

## backlog-apiでの取り扱い指針

- ログや内部状態をAPIキー単位として表現しない
- 複数組織構成では、選択されたBacklog接続先ごとにレート制限情報を分離する
- `X-RateLimit-Reset`を表示する場合は、検証済みUNIX秒をISO 8601 UTCへ変換し、
  CLI独自フィールド`rateLimitResetAt`として扱う
- verboseログでは3つのレート制限ヘッダーだけをホワイトリストで取得し、URL、
  APIキー、レスポンス本文、その他のヘッダーを出力しない
- ヘッダーからリクエスト種別を確定できない場合は、`read`などを推測して記録しない
- 明示的なレート制限取得操作を追加する場合は、既存の上流由来58操作とは異なる
  Node CLI独自操作であることをトレース情報へ記録する

公開済みの`backlog-api` v0.3.3では、内部SDKの`getRateLimit()`は利用可能ですが、
`get_rate_limit`操作としては公開されておらず、verbose層もレスポンスヘッダーを
捕捉していません。
